# MiniMesh 技术调研方案

## 1. 调研目标

调研目标不是直接复制成熟 Service Mesh，而是回答：

1. 成熟方案如何划分控制面和数据面？
2. 哪些设计值得 MiniMesh 借鉴？
3. 哪些能力应该自行实现？
4. MVP 应控制到什么范围？
5. Go 是否适合承担 Sidecar 和 Control Plane？

---

## 2. 重点参考项目

重点研究：

- Control Plane / Data Plane 分离
- Sidecar 模式
- 服务发现
- 流量治理
- 配置模型
- Telemetry

- Listener

- Endpoint

- Load Balancing
- Circuit Breaking

### 2.3 Linkerd

重点研究：

- 轻量级 Service Mesh 的设计取舍
- Rust 数据面设计
- Proxy 与 Control Plane 的边界
- 可观测性

它也是后期引入 Rust 时的重要参考。

### 2.4 gRPC

重点研究：

- HTTP/2 多路复用
- Stream
- Deadline
- Metadata
- Keepalive
- Connection Management
- Health Checking
- Load Balancing

### 2.5 etcd

重点研究：

- Lease
- Watch
- Revision
- Compaction
- Leader Election
- 一致性模型

## 3. 核心技术问题

### 3.1 Sidecar 请求代理

需要调研：

```text
Business Service
      |
 localhost
      |
    Sidecar
      |
 Remote Sidecar / Service
```

重点问题：

- Sidecar 如何确定目标服务？
- 请求协议如何携带 service/method？
- gRPC 请求是透明代理还是重新建立调用？
- 如何维护后端连接？
- HTTP/2 如何复用连接？

### 3.2 服务发现

候选方案：

| 方案 | 评价 |
|---|---|
| etcd | 首选，Lease/Watch/强一致适合注册中心 |
| Consul | 成熟，但会增加新的体系 |
| Redis | 可实现，但不是本项目首选 |
| 自研 | 学习价值高但前期成本过大 |

初步决定：**etcd**。

### 3.3 Control Plane → Sidecar 配置下发

候选：

- HTTP Polling
- WebSocket
- gRPC Server Streaming
- gRPC Bidirectional Streaming

初步选择：

**gRPC 双向流。**

消息采用统一 Envelope：

```protobuf
message ControlMessage {
  uint64 version = 1;

  oneof payload {
    Register register = 10;
    Heartbeat heartbeat = 11;
    RouteUpdate route_update = 12;
    EndpointUpdate endpoint_update = 13;
    Ack ack = 14;
  }
}
```

重点研究：

- ACK
- Revision
- 重连
- Full Sync
- Incremental Update
- 消息乱序
- 幂等

### 3.4 负载均衡

阶段性实现：

1. Round Robin
2. Weighted Round Robin
3. Least Connections
4. Consistent Hash（可选）

需要建立统一接口：

```text
Picker
  |
  +-- RoundRobin
  +-- Weighted
  +-- LeastConn
```

### 3.5 Retry

重点研究：

- 哪些错误允许重试？
- 最大重试次数
- Backoff
- Retry Budget
- 幂等请求
- Retry Storm

禁止简单无脑重试所有请求。

### 3.6 Circuit Breaker

研究：

- Closed
- Open
- Half-Open

指标：

- 请求数量
- 失败率
- 连续失败
- 时间窗口

自行实现状态机，而非完全依赖第三方库。

### 3.7 Rate Limit

第一阶段：

- Token Bucket
- 单 Sidecar 本地限流

后续：

- 服务级规则
- 分布式限流

### 3.8 可观测性

统一观测链路：

```text
Business
   |
Sidecar
   +---- Metrics ----> Prometheus
   |
   +---- Trace ------> OTel Collector / Jaeger
   |
   +---- Logs
```

重点指标：

- request_total
- request_duration
- active_connections
- retry_total
- circuit_breaker_open_total
- rate_limit_rejected_total

---

## 5. Rust 引入调研

Rust 不参与 MVP 核心链路。

计划在系统稳定后调研：

### 方向 A：Rust Service

实现 Rust gRPC 服务，验证语言无关性。

### 方向 B：Rust Agent

采集：

- TCP Connection
- RTT
- Socket State
- Network Metrics

### 方向 C：eBPF

研究：

```text
eBPF
 |
Rust Agent
 |
gRPC
 |
Go Control Plane
```

可参考 Aya 等 Rust eBPF 生态。

### 方向 D：性能组件

仅当 Benchmark 证明 Go 模块存在明确瓶颈后，尝试 Rust 重写并进行对比。

---

## 6. C++ 调研定位

C++ 暂不作为主要开发语言。

适合：

- C++ gRPC 服务兼容测试
- 高性能 Benchmark Worker
- 与既有 C/C++ 系统集成
- FFI 实验

如果没有明确场景，不为“增加语言数量”而引入。

## 9. Benchmark 方案

建立基线：

### Direct

```text
Client -> Service
```

### Mesh

```text
Client -> Sidecar -> Service
```

比较：

- QPS
- Avg latency
- P50
- P95
- P99
- CPU
- Memory
- Goroutine
- GC

目标不是宣称超过 Envoy，而是能够量化 MiniMesh 引入的代理开销。

---

## 10. 调研输出要求

每项重要技术决策形成简短 ADR：

```text
问题
候选方案
选择
理由
代价
未来调整条件
```

禁止只写“因为性能好”“因为流行”。

所有优化必须具备：

**问题 → 数据 → 方案 → Benchmark → 结论**

的完整证据链。
