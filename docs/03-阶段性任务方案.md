# MiniMesh 阶段性任务方案

## 总体规则

项目采用阶段式开发。

每个 Stage 必须同时满足：

1. 阶段功能完成
2. 单元/集成测试通过
3. README 或 docs 更新
4. 可独立运行 Demo
5. 达到验收标准

未通过当前 Stage 验收，不进入下一阶段。

---

完成：

# Stage 1：基础 gRPC Proxy

## 目标

实现最小可用 Go Sidecar。

## 链路

```text
Client
  |
Sidecar
  |
Go Backend
```

## 任务

- 定义基础 RPC 协议
- Sidecar 接收请求
- Sidecar 转发请求
- Context/Deadline 传递
- Metadata 传递
- 基础错误映射

## 测试

验证：

- 正常请求
- Backend 不存在
- Backend 超时
- 并发请求
- Deadline

## 验收

至少 1000 个并发请求下代理链路稳定，无明显 goroutine 泄漏。

---

# Stage 2：服务注册与发现

## 目标

引入 etcd，实现动态服务发现。

## 任务

Control Plane：

- Service Register
- Deregister
- Lease
- Heartbeat
- Endpoint 管理

Sidecar：

- Endpoint Cache
- Watch
- Full Sync
- Revision

## 测试

模拟：

1. Service A 上线
2. Sidecar 获取 Endpoint
3. 新实例上线
4. Sidecar 自动更新
5. 实例宕机
6. Lease 过期
7. Endpoint 自动删除

## 验收

业务无需重启即可感知实例上线和下线。

---

# Stage 3：负载均衡

## 目标

支持多实例服务。

## 任务

实现统一 Picker 接口。

实现：

- Round Robin
- Weighted Round Robin
- Least Connections

Endpoint 更新时支持无锁或低锁更新策略。

## 测试

启动三个 Backend。

发送 10,000 次请求。

验证：

- RR 分布
- Weight 分布
- LeastConn 行为
- Endpoint 动态加入/删除

## 验收

负载分配符合算法预期，节点变化过程中请求链路保持稳定。

---

# Stage 4：连接管理

## 目标

避免每个请求重新建立连接。

## 任务

实现：

- Connection Pool
- Idle Connection
- Max Connection
- Connection Reuse
- Keepalive
- Graceful Close

重点记录：

- active connections
- idle connections
- connection creation total

## 测试

比较：

```text
No Pool
vs
Connection Pool
```

Benchmark：

- QPS
- P99
- CPU
- Connection 数量

## 验收

通过数据证明连接复用有效。

---

# Stage 5：Retry + Timeout

## 目标

实现基本容错。

## 任务

Timeout：

- Request Timeout
- Context Deadline

Retry：

- Max Attempts
- Backoff
- Retryable Status
- Retry Budget

## 测试

构造：

- Backend 500
- Backend timeout
- Backend 短暂不可用
- 部分实例异常

## 验收

异常实例不会导致整个服务立即不可用，并且不存在无限重试。

---

# Stage 6：Circuit Breaker

## 目标

实现熔断器。

## 状态

```text
Closed
  |
failure threshold
  v
Open
  |
cooldown
  v
Half-Open
  |
success / failure
```

## 任务

实现：

- 状态机
- Sliding Window
- Failure Rate
- Minimum Requests
- Cooldown
- Probe Requests

## 测试

制造 80% 错误率。

验证：

- 自动 Open
- Open 状态快速失败
- 冷却后 Half-Open
- 服务恢复后 Closed

## 验收

熔断状态转换符合设计，不出现明显并发竞争问题。

---

# Stage 7：Rate Limit

## 目标

保护后端服务。

## 任务

实现 Token Bucket：

- rate
- burst
- service rule
- route rule

第一阶段本地限流。

## 测试

例如：

```text
limit = 1000 req/s
input = 5000 req/s
```

验证：

- 放行量
- 拒绝量
- Burst 行为

## 验收

限流误差处于可接受范围，并暴露相关 Metrics。

---

# Stage 8：Control Stream

## 目标

建立正式 Control Plane ↔ Sidecar 长连接。

## 任务

使用 gRPC Bidirectional Stream。

支持：

- Register
- Heartbeat
- EndpointUpdate
- RouteUpdate
- ACK
- Version
- Reconnect
- Full Sync

## 测试

重点测试：

- Control Plane 重启
- Sidecar 重启
- 网络断开
- 重复消息
- 乱序版本
- ACK 丢失

## 验收

断线恢复后 Sidecar 最终能得到正确配置。

# 推荐开发顺序总结

```text
Stage 0  工程初始化
   ↓
Stage 1  Proxy
   ↓
Stage 2  Discovery
   ↓
Stage 3  Load Balance
   ↓
Stage 4  Connection Pool
   ↓
Stage 5  Retry / Timeout
   ↓
Stage 6  Circuit Breaker
   ↓
Stage 7  Rate Limit
   ↓
Stage 8  Control Stream
   ↓
Stage 9  Java + Python
   ↓
Stage 10 Observability
   ↓
Stage 11 Performance
   ↓
Stage 12 Rust (Deferred)
   ↓
Stage 13 Kubernetes (Completed)
   ↓
Stage 14 Transparent Proxy (Completed)
   ↓
Stage 15 Security (Completed)
   ↓
Stage 16 Final Validation
```

其中 **Stage 0～10 是项目主体**；Stage 11～16 用于把项目从“能运行”提升到“有工程深度、可用于面试深挖”的程度。
